# Developer setup and PostgreSQL formatting

On Ubuntu/Debian, first install the project Go version from go.mod yourself, then:

```sh
make install-system-deps
make setup-dev
```

If prerequisites are already installed, run only `make setup-dev`. System packages
are a separate, explicit concern: `install-tools` and `setup-dev` never invoke
sudo or apt. The system target detects Ubuntu/Debian/apt, lists only missing
packages, skips installed packages, and explains sudo before using it. Unsupported
systems get manual-install guidance. It never installs/replaces Go or changes
unrelated system configuration.

Required packages are ca-certificates, curl, git, make, tar, gzip, coreutils,
findutils, perl, build-essential (existing Go CGO/race checks), and
protobuf-compiler (existing proto generation). Full distro Perl supplies the
CLI core modules and MakeMaker, including autodie, Encode, Text::Wrap,
Getopt::Long, File::Basename, FindBin and Carp. CGI and JSON are optional upstream
web-interface dependencies, not needed or installed here. No CPAN installation
is performed. Docker/Compose and service credentials remain explicit manual setup.

`setup-dev` checks prerequisites and the exact Go version declared in go.mod,
reuses `install-tools`, verifies all installed tools and the existing hook, and
uses the existing safe `.env`/HTTP-client example targets. Existing local config
is retained. No containers, SQL execution, database initialization/migration,
cleanup/reset or privileged command runs. Repeated hook installation skips an
already configured executable `.githooks/pre-commit`. Ensure the reported Go bin
directory is in your interactive PATH for the existing Go/lint hook checks.

## Tool installation

- `make install-tools`: all existing Go tools and generators, pgFormatter, hooks.
- `make install-pg-formatter`: only the pinned user-local formatter.
- `make setup-dev`: validated, non-destructive environment preparation.

Previously moving Go tool installs now have configurable pinned versions too;
no tools are added to application go.mod. GOTOOLCHAIN=local prevents these
installers from downloading/replacing Go. The existing official golangci-lint
installer is fetched from the selected release tag rather than a moving script.

pgFormatter is pinned to **5.11** in `scripts/pgformatter.lock`. The installer uses
the [official tagged source archive](https://github.com/darold/pgFormatter/tree/v5.11)
and upstream `perl Makefile.PL`, `make`, `make install`, with MakeMaker INSTALL_BASE
pointing at a temporary user prefix. It verifies the repository-pinned SHA-256
**before extraction**, checks the version, publishes a versioned installation and
cleans temporary files. The official RealBin/lib lookup finds the installed modules
through a relative symlink, without personal PERL5LIB settings.

Default executable:
`~/.local/share/bnpl-tools/pgFormatter/5.11/bin/pg_format` (or XDG_DATA_HOME).
Make and the hook resolve it explicitly; interactive PATH is not required for SQL.
Override PG_FORMATTER_INSTALL_DIR for another absolute user-owned prefix, or
PG_FORMATTER to select an existing executable of the pinned version. Installers
never overwrite another version/incomplete directory or a system installation.
Version overrides require an explicitly reviewed PG_FORMATTER_SHA256. Update the
shared lock in a reviewed tooling change so local, staged and CI checks agree.

Upstream publishes an autogenerated tagged archive, without a release checksum
asset/signature for this release. The checked-in digest records the reviewed
HTTPS download; it is an integrity pin, not a claim of independently signed origin.
Later changed archive bytes fail closed. Do not automatically replace a checksum
on failure; inspect the official tag/release provenance first.

## SQL workflow

```sh
make sql-fmt
make sql-fmt-check
# Format only selected paths, safely including spaces/special characters:
bash scripts/sql-format.sh fmt -- 'path with spaces.sql'
git add -p
# or: git add -- 'path with spaces.sql'
git commit -m "..."
```

`.pg_format` is the sole formatting policy: 4 spaces, uppercase keywords, lowercase
data types where upstream supports them, retained comments, no anonymization,
no truncation and preserved parentheses. Personal HOME/XDG rc files are disabled.
Hard wrapping is intentionally disabled: upstream wrap-limit can insert newlines
inside SQL literals, changing their values. Use a soft 120-column editor guide;
structural formatting does not guarantee a hard line-length cap. A bounded fixed
point handles upstream multi-pass layouts consistently in fmt/check/hook. Failure
to converge fails without rewriting that file.

All maintained nonignored SQL files are included: incremental migrations,
canonical embedded bootstrap/seed SQL and audits. Generated/vendor/third-party,
build/temp files and symlink aliases under assets/db/init are skipped; their
canonical source files are included. SQL inside Go strings is not changed.
Whitespace, newlines and shell-special characters in SQL filenames are supported.
Formatting replaces only changed files, preserving modes. Check mode only compares
temporary output and never writes SQL or the Git index. No SQL statements execute.

The existing Git pre-commit hook now validates added/modified/renamed/copied SQL
**from exact index blobs**, not working-tree contents. It also reads the staged
formatter policy, so unstaged policy changes cannot mask a staged error. Deleted
SQL is skipped; no staged SQL means no formatter requirement. Missing/wrong-version
formatter or bad formatting blocks the commit with paths and installation/fix
instructions. It never formats, stages, resets or changes developer files.
The original golangci-lint configuration, tidy-diff and lint checks are retained.
Always restage intended SQL after formatting, particularly after `git add -p`.

The CI SQL-format job installs the same pinned artifact, runs
`make sql-fmt-check` and the isolated tooling tests. It does not run apt, a
migration or SQL, and never formats files in CI. All previous CI/CD checks remain;
application Docker images and deployment workflows are unchanged.

## Pre-production checksum handoff

For this adoption the user explicitly requested formatting **all current SQL**:
there is no legacy hash exemption or grandfather list. The baseline and existing
migrations were reformatted too. Registered baseline/migration/function-body hashes
were deliberately left untouched for the user to update manually. See
[verification and new digest inventory](pgformatter-verification.md). Until that
handoff is completed, checksum tests/DB initialization/startup compatibility checks
can correctly fail; formatting checks passing does not mean those hashes match.
An existing local DB may retain old migration checksums as well. No database was
reset or updated by this tooling task. Before first production release, freeze the
baseline and treat published incremental SQL as immutable: format new SQL before
it is applied, and use new migrations for later changes rather than reformatting
published history.

## Troubleshooting and verification

- Missing Perl/system commands: run `make install-system-deps` explicitly, or have
  the administrator repair/install distro Perl modules. Do not use unpinned CPAN.
- Formatter missing/version mismatch: `make install-pg-formatter`; check
  PG_FORMATTER and the printed user prefix. Choose a new prefix rather than
  overwriting an unrelated installation.
- Bad formatting: run sql-fmt, inspect the diff, restage and retry. A clean working
  file does not fix a different bad staged blob.
- SHA mismatch: verify the pinned release provenance; the installer refuses it.
- Run `make test-dev-tooling` for isolated Git-commit/index tests, installer
  integrity/idempotency and safe setup/system-dependency tests. It uses the real
  formatter, mocks Go/lint/privileged operations for fixtures, and performs one
  clean formatter download into temporary user storage. No database is needed.
